# Security

The cloud is designed around a conservative trust boundary.

## App trust boundary lint

Run `scripts/ihc-app.sh lint [<dir>]` before deploying (the directory defaults to the
current directory). It exits non-zero with one line per finding. The template's deploy
workflow runs `ihc-app lint` after checkout and before build. The linter needs PyYAML,
included in the deployer image; in a development checkout it can use the portal's
installed Node `yaml` package instead. It never executes app code or loads app `.env`.

It reuses the executor's manifest, Compose and build validators, including their
diagnostics for local infrastructure, privileged containers, host networking, Docker
socket mounts and builds that read outside the repository. Additional checks refuse
added capabilities, devices, host namespaces, lifecycle hooks, unresolved isolation or
build variables, Compose includes/extends and host-backed or external named volumes.
Bind mounts, even read-only ones, must stay inside this app's
`<install-dir>/app-data/<slug>/`; traversal and symlinks cannot escape it. Ordinary
app-owned named volumes are allowed.

Repository files cannot supply host cron entries, systemd units/timers, deploy hooks,
setuid/setgid executables or files laid out for privileged host binary directories.
Workflow and shell-script checks flag host paths and privileged host commands;
workflows also flag privileged containers, added capabilities, host namespaces and
Docker sockets. Put host installation code in the protected platform checkout.

`install.sh doctor` runs the same lint over each installed app's active release (or
its Compose source directory for older deploys). Findings are warnings with evidence
and a repair action. It also inspects running bind mounts for overlap with platform
paths. `--install-dir` / `IHC_INSTALL_DIR` select the installation, defaulting to
`/opt/inhousecloud`: the entire installation is platform-owned except the app's own
data subtree. This protects `compose.yml`, `.env`, `runner/`, `portal/`, `catalog/`,
`local/`, backups and other apps from a second manager. Missing source or an unavailable
YAML reader is a warning, never a successful lint.

This static check supports review; it cannot prove what arbitrary shell code does.
The repository owns its workflow and can remove the lint step. The deploy runner's
Docker socket remains root-equivalent, as described below.

## Trust Boundary

- Coding agents may edit files and open pull requests.
- Pull requests run validation on the CI runner, without secrets, the Docker socket or the ihc network.
- Real deploys happen only on a push to `main`: that push is the approval.
- The deploy runner serves the organization's repositories only. Its jobs have the Docker socket and the install directory, so a deploy job is root on the box: write access in the organization is box access ([`gitops-flow.md`](gitops-flow.md)).
- **Who builds is not who applies.** The template's deploy is two steps ([`gitops-flow.md`](gitops-flow.md#3-what-the-deploy-job-does)): `ihc-app build` makes a release from the commit's files only, without the install's credentials and without anything Compose would read from the machine (build secrets, SSH agent, host network, contexts outside the repository); `ihc-app apply` is the only step that changes the app, under a per-app lock, and only for the commit at the head of `main` in Gitea. It never builds or pulls: it starts the images the build tagged for that release. What this does not close yet: the steps share one job with the socket, and a repository's own workflow can skip `apply` and call `docker` on any branch push. Taking the socket out of deploy jobs, with the reconciler outside them and the build as an unprivileged user, is the follow-up.
- **Every deploy is journaled before it changes anything**, and can be rolled back. The journal (`<install-dir>/catalog/deploys/<slug>.jsonl`, append-only) records the release, commit and images before and after, the overlay's sha256 and the env file's key names, never a value; admins read it in the portal and with `ihc-app journal`. `ihc-app rollback` is run on the box by a person, takes the same lock, is journaled and health-checked, and never retries on its own.
- Credentials live on the box: the install `.env` and each app's `apps/<slug>/.env`, mode 0600, never in Git, never printed.
- **The portal's API token reads, and only one route.** `IHC_PORTAL_API_TOKEN` (generated by `first-run.sh` into `.env`, never printed, fingerprint in `state.json`) opens `GET /api/platform/status` without a session, for agents and the installer ([`portal-api.md`](portal-api.md)). With it, every other portal route answers 403; a wrong token is 401; a portal without one answers 503. On the proxy only that exact path, and only when the request carries an `Authorization` header, skips the forward auth (`scripts/lib/portal-api.sh`); the proxy drops any `X-authentik-*` header on that request, so a token can never pass as a person. The response carries no secret: service health, public URLs and the installation's topology. What it does reveal to a token holder is which services exist and which are down, so it lives in `.env` like every other credential and the agent profile does not receive it (smoke test 23).
- **Object storage: the root credentials never reach an app.** Garage's RPC secret, admin token and metrics token are in the install `.env` only. Each app gets its own access key, allowed to read and write its bucket `app-<slug>` and nothing else: not owner (no bucket policy or deletion), no bucket creation, 403 on another app's bucket (smoke test 19). The admin API listens on `garage:3903` with a token and is not routed by the proxy; the RPC port answers only to the RPC secret. `s3.<BASE_DOMAIN>` is public to whoever reaches the proxy, like any S3 endpoint: every request must be signed by a key. Provision sends secrets to Garage on stdin, never on a command line.

## Ops tools: admin access to the machine

The `ops` profile (on by default in the interactive installer) adds four tools for `ihc-admins`. Treat membership of that group as root on the box:

- **Web terminal (`terminal.<BASE_DOMAIN>`, Wetty) is a shell on the host** as the user that ran `install.sh`, who is in the `docker` group or runs rootless Docker: equivalent to root on the box. It signs in with a dedicated key, `<install-dir>/local/wetty/id_ed25519`, whose public half sits in that user's `~/.ssh/authorized_keys` (comment `ihc-wetty@<host>`). To revoke it, delete that line; to rotate it, delete the line and the two key files and re-run `install.sh --apply --from optional_profiles`. The key is in the backup (the install directory is backed up), encrypted with the backup key.
- **File browser (`files.<BASE_DOMAIN>`, FileBrowser) sees every app's data**, read and write, and the backup reports, read only. What it does **not** mount, on purpose: the install directory itself, `.env` (every platform secret), `apps/` (each app's `.env` with its database password), `local/` (the terminal key), `runner/`, `state.json`, `config.yaml`, the restic repository, home directories and system directories. App data lives in `<install-dir>/app-data/<slug>`, apart from `apps/<slug>/`, precisely so it can be shown without the secrets next to it. The installer refuses a configured path that breaks this rule, and `scripts/tests/ops-mounts.sh` fails if the compose file ever mounts the install directory or an env file into it.
- **Portainer** has the Docker socket (root on the box) and **Glances** sees every process: both were already admin tools; they now require `ihc-admins` too.
- **No way around the SSO.** The four run on the `ihc-ops` network, which only the proxy joins; apps on the `ihc` network cannot reach them directly. They publish no host port and their routes leave no path public. FileBrowser trusts the `X-authentik-username` header only because nothing but the proxy can reach it.
- **The smoke user.** First-run keeps `ihc-smoke-user` in `ihc-users` (no admin rights; password only in `.env`, 0600; email `ihc-smoke-user@smoke.invalid`, a domain that never receives mail) so smoke tests 18 and 24 can prove the denials with a real sign-in. It can open Gitea, the apps and the portal's catalog like any user; deactivate it in Authentik if you do not want it, and tests 18 and 24 will then fail at the sign-in rather than at the denial.

## The portal: who sees what, and its Authentik account

The portal's route lets in `ihc-admins` and `ihc-users` (two policy bindings on the `portal` application in Authentik); anyone else is refused by Authentik after signing in. Inside, the role comes from the groups the outpost sends (`X-authentik-groups`, trusted only from the proxy):

| | `ihc-users` (viewer) | `ihc-admins` (admin) |
|---|---|---|
| Catalog: apps, health, SSO, deploys | yes | yes |
| Platform (`/api/platform/status`), storage usage | 403 | yes |
| Dockers page | hidden (the runtime JSON under `/api/runtime/*` and `/api/apps-runtime` still answers: container names, images, state) | yes |
| People and groups (`/api/people`, `/api/groups`) | 403 | yes |
| Disk snapshots, portal admins | 403 | super admin only |

**The service account `ihc-portal`.** The People page reads Authentik with its own account, not with an admin's: first-run creates the user `ihc-portal` (type service account, no password, cannot sign in interactively, in no group), a role `ihc-portal-reader` with exactly two global permissions, `authentik_core.view_user` and `authentik_core.view_group`, and one API token (`ihc-portal-api`, intent API, no expiry), whose key goes to `AUTHENTIK_PORTAL_TOKEN` in `.env` (0600) and from there only into the portal's container.

- **It can:** list users (username, name, email, active, last login, groups) and groups (name, members), which is what the page shows.
- **It cannot:** create, change or delete anything (users, groups, passwords, tokens, applications, policies, flows), view or create other tokens, impersonate, or read any other model (providers, applications, events). A `POST` that would create a group answers 403 (smoke test 24 checks it on every install). It never sees passwords: Authentik never returns them.
- **Re-running first-run** (or `install.sh --apply --from foundation`) puts the role back to those two permissions, removing any other a human may have added, and keeps the token while it still works; a token that stopped working (deleted or rotated in Authentik) is replaced and `.env` updated.
- **To revoke:** Authentik > Directory > Tokens > `ihc-portal-api` > Delete (the People page then answers 503 until first-run runs again), or deactivate the user `ihc-portal`.
- **What it reveals if leaked:** the directory (who works here, their emails and groups). Not a way in: no password, no write.

Every route of the portal, who reaches it and what still writes: [`portal/docs/SECURITY.md`](../portal/docs/SECURITY.md).

## The MCP gateway: agents acting as a person

The gateway ([`mcp-gateway.md`](mcp-gateway.md)) lets an AI client act as the signed-in person. What bounds it:

- **Who enters.** Only someone who signs in to Authentik and is in `ihc-users`: the application `ihc-mcp` is bound to that group (Authentik refuses the code to anyone else), and the gateway checks the `groups` of every token again (403 otherwise). Admin tools (platform status, people, groups) need `ihc-admins` in the token, as the portal's pages do.
- **The client.** `ihc-mcp` is a public OAuth client: no secret exists to leak, PKCE binds the code to the program that asked, consent is explicit (a program on the person's laptop cannot get a token without a page the person clicks), and redirects go only to claude.ai, claude.com, loopback addresses and what `MCP_OAUTH_EXTRA_REDIRECT_URIS` adds. Access tokens live one hour; refresh tokens 30 days, and a deactivated person can neither sign in nor refresh. To cut someone off: deactivate the user or remove them from `ihc-users` (the next token check or refresh fails); to cut every client: Authentik > Applications > Providers > `ihc-mcp` > revoke its tokens, or remove the binding.
- **The token never reaches an app.** Apps get a different token, the actor JWT, signed by the gateway's own key, valid five minutes, for one app (`aud`) and with only the scopes that app's manifest grants the person's groups. An app (or someone who compromised one) cannot replay it against another app, the gateway, Authentik, Gitea or the portal. The gateway's private key stays in the `mcp-keys` volume; its public half is published.
- **The app decides.** The gateway proves who is asking; the app filters what that person may see, exactly as for a browser user. A tool that ignores `actor.email` shows everyone everything to anyone the manifest grants.
- **Grants per tool.** Beyond the scopes, `mcp.tools.<tool>.groups` and `.people` in the manifest narrow one tool to some Authentik groups or some people. The gateway hides that tool from everyone else and refuses their call without calling the app. A tool without an entry keeps the scope as its only rule, which is how every install worked before. A malformed entry takes the whole app out of the gateway rather than granting more.
- **Reaching apps.** The gateway calls apps on the cloud network at `http://<slug>:<runtime.port>` and the paths of their manifest (paths only, no host: an app cannot point the gateway elsewhere). Their `/mcp/*` routes are also behind the forward auth through the proxy, where a browser without an actor JWT gets 401.
- **The platform's tools read.** The `ihc_*` tools read the inventory, the portal's status API, Authentik with the read-only account and, for admins, the audit log. Writes exist only as app tools, under the rules below.
- **What the gateway holds:** the portal's status token and the read-only Authentik token (the same as the portal's), the inventory read only, its signing key, and the password of its audit role (`MCP_AUDIT_DB_PASSWORD`), which can insert into and read one table. No Docker access, no `.env`, not the portal's database role. Its logs name the person and the tool, never a token.
- **What a leaked access token gives:** one hour of that person's tools: the reads, and the writes their grants allow, each of which still needs an approver who exists in the directory and lands in the audit log under that person's name. Revoke it in Authentik (the user's sessions and tokens).

### Writes need a human

In the cloud's agent products a write happens only after a person approves it on a screen. The gateway holds the same line for every app's tools, whatever client calls them:

- **Read or write.** A tool is a read only when the app's tool list or the manifest (`mcp.tools.<tool>.access`) says `read` and neither says `write`. Undeclared is a write; an app that cannot be asked counts as undeclared. A tool cannot list itself as a write and claim `readOnlyHint: true`: the gateway sets the hint from its own decision.
- **`confirmed_by`.** Every write needs the email (or username) of the person who approved it. The gateway refuses the call without it, and resolves it in the company directory (Authentik, read-only account): an active person in `ihc-users`, matched by email or username, never by display name or free text. No directory configured, or the directory not answering: writes are refused. The app receives the approver as the actor JWT's `confirmed_by` claim, the email as the directory has it, and `confirmed_by` is removed from the arguments it gets.
- **What `confirmed_by` proves.** That the approver exists and is named on the record, not that they clicked: an agent can still name the person it acts for without asking. The click belongs in the client (a confirmation the person answers), and the audit makes a false attribution traceable afterwards. The actor and the approver may be the same person; the record says so (`confirmed_by_is_actor`).
- **The audit log is the gateway's, not the app's.** It lives in the portal's database (`deploy_platform.mcp_audit_log`, migration 010), which no app can reach: apps get their own database roles, and the portal's database refuses connections from any role but its owner and the gateway's audit role. An app cannot write, change or delete an entry, and nothing it returns is trusted beyond the `previous`/`new` values it reports for its own write. (The weakness this avoids: an audit written by the tool itself, from inside its sandbox, onto a volume the tool can also rewrite.)
- **No audit row, no write.** The gateway records `requested` (actor, approver, tool, app, arguments) before calling the app; if that insert fails, the app is not called. After the call it records `completed` with the status, the error code and the app's previous and new value. A `requested` without `completed` reads as `unknown`: the gateway stopped between the two, or the second insert failed, and the write may or may not have happened. Refused writes (no or unknown approver) are recorded too.
- **Append-only, twice.** The gateway connects as `ihc_mcp_audit` (`MCP_AUDIT_DB_ROLE`, created by `install.sh` in stage `portal`): `NOSUPERUSER NOINHERIT`, `CONNECT` on the portal's database, `USAGE` on its schema, `SELECT` and `INSERT` on that one table, nothing else; every run of the stage puts the grants back to exactly these, and smoke test 13 checks them. On top of that, triggers on the table refuse `UPDATE`, `DELETE` and `TRUNCATE` for every role, the owner included. Removing an entry takes the portal's owner role or the Postgres superuser (both only in the install `.env`) and dropping a trigger first. There is no retention job: the log grows with the writes.
- **Secrets.** Arguments and the previous and new values are stored with secrets redacted: any key that looks like a secret (`password`, `token`, `api_key`, `authorization`, `cookie`, `secret`, `credential`, `private_key`, …) and any value that looks like one (a JWT, `Bearer …`, a PEM private key, tokens with a known prefix). Long strings, lists and nesting are cut, and a payload over 64 KiB is stored as a preview. Redaction is a net, not a guarantee: an app should not take secrets as tool arguments.
- **Who reads it.** Admins (`ihc-admins`): the MCP tool `ihc_audit_log` and the portal's `GET /api/mcp/audit` (filters: app, tool, actor, confirmed_by, since). Nobody edits it through either.
- **Off until configured.** Without `MCP_AUDIT_DATABASE_URL` (an install that has not re-run `install.sh --apply --from foundation`), every write is refused with a message saying so; reads work as before.

## Private ingress: the tailnet and the CA

`INGRESS=private` ([`install-design.md`](install-design.md#private-ingress-private--internal--tailscale)) puts the box on the company's tailnet. What that exposes and what it trusts:

- **What the tailnet reaches.** Ports 80 and 443 (the proxy, so every route with its SSO), the Gitea SSH port (Gitea's SSH, keys only) and 53 (the split-DNS server, which answers only for `BASE_DOMAIN`). Nothing else: the Tailscale node runs in its own network namespace, so the proxy admin (81), the control ports and every container stay off the tailnet. Smoke test 21 proves the admin port is refused on the tailnet address. Who on the tailnet may reach the node at all is the tailnet's access policy (ACLs or grants): restrict it to the people who should see the apps.
- **What the LAN reaches.** Nothing: in `private` the proxy and Gitea SSH are published on 127.0.0.1 only (smoke test 21 checks the bindings and that the box's other addresses refuse 80 and 443).
- **The auth key** (`IHC_TAILSCALE_AUTHKEY`) is used once, from the installer's environment: it is not in `.env`, not in the compose file and not in the running container. The node's identity is the state in the volume `tailscale-state` (in the backup, encrypted with the backup key); whoever has that volume can impersonate the node, so treat it like a key. To revoke: remove the node in the Tailscale admin console. Prefer a pre-approved, tagged, reusable or one-off key; an ephemeral key's node disappears from the tailnet some time after the box goes offline and a new key is then needed.
- **The CA.** `<install-dir>/local/ca/ca.key` (0600) can sign certificates that every device with the CA installed accepts. Its name constraint limits that to `BASE_DOMAIN` and its subdomains (no other domain, no IP address), so a stolen key cannot impersonate a bank or a public site to those devices. It never leaves the box except in the encrypted backup. `ca.crt` is public. The wildcard key also lives in the proxy's data volume (it serves it).
- **Client addresses.** The proxy sees the Tailscale node as the client of every tailnet request (`X-Forwarded-For` holds the node's container address), not the person's tailnet address: per-person attribution comes from the SSO, not from the network.

## The operator agent: the largest surface of the installation

The `agent` profile (off by default) runs an LLM agent on the box that reads chat messages, logs and web pages, any of which can carry instructions written by someone else. It is therefore built to hold nothing whose loss would be worse than a wrong answer. Its rules are [`operator-contract.md`](operator-contract.md); this is what it can technically reach.

| It sees | How |
|---|---|
| Containers, images, networks, volumes, disk usage, logs, process lists, stats | `docker-ro`, a read-only filter in front of the Docker socket (`docker/agent/docker-ro-proxy.py`), a core service the portal reads through too (on its own internal network, `ihc-docker`; the agent knows it as `agent-docker-proxy` on `ihc-agent`): GET on an allowlist only; logs and stats never stream. **Every `Env` in a container or image inspect comes back as names only**: a plain socket proxy that allows `GET /containers/<id>/json` hands out every service's passwords, the backup key included |
| Every service on the `ihc` network, by name | it joins `ihc` to run HTTP checks the way the proxy does (`http://proxy/` with a `Host` header, health endpoints). It holds no database or admin credential for any of them |
| Gitea, read only | `GITEA_READONLY_TOKEN` (read:misc, read:repository, read:organization, read:user) |
| The backup status | `<BACKUP_DESTINATION>/reports`, mounted read only |
| The map of the box | `<install-dir>/agent/reference/` (read only): the contract, the runbooks, the generated brief (names and places of credentials, never values; the generator refuses to write one that contains a value) |
| Its own LLM key and chat tokens | `AGENT_*` in `.env`, written by a human, passed to its container by name |

| It does not see | Why |
|---|---|
| The Docker socket | only the filter has it; the filter's network (`ihc-agent`) is internal |
| The install directory, `.env`, `apps/` (the apps' env files), `local/` (keys), `state.json`'s directory | not mounted; smoke test 20 checks every mount source |
| Any cloud secret in its environment | only `GITEA_READONLY_TOKEN` and `AGENT_*`; smoke test 20 compares its environment with `.env` |
| The ops tools | not on `ihc-ops` |
| A shell on the host | none; what needs the host, it asks a human to run |
| A port or route | the gateway listens on the container's loopback; people reach it through the chat channel only |

Writes. By default none: every POST, PUT, DELETE through the filter answers 403, and the agent cannot restart even an app. `ops.agent.allow_write: true` adds exactly two: `POST /containers/<id>/restart` for a container of an app's Compose project (never one of the `ihc` project) and `POST /build/prune` (the build cache, never images or volumes), and only from the agent's container (`WRITE_CLIENTS`: the portal, on the same filter, never writes). Nothing else is ever on the list: no exec (exec is a shell), no create, no image or volume removal. Re-running a deploy needs a Gitea token that a human creates for it (`AGENT_GITEA_TOKEN`). Each request through the filter is logged (`docker compose logs docker-ro`).

Who can talk to it. `ops.agent.allow_from` lists chat user ids; empty means pairing, and the admin approves each first DM (`docker compose exec agent node dist/index.js pairing approve <channel> <code>`). Anyone who can talk to it can make it read anything above and repeat it in the chat, logs included: keep the allow list to people who could read the logs anyway. Its LLM provider receives what it reads. In a Telegram group it answers only in the chats listed in `ops.agent.groups`, only when the message mentions the bot, and only to the senders in `ops.agent.group_allow_from` (default `allow_from`): a DM pairing never authorizes anyone in a group, and an empty list means no group at all. Another bot in the group is a sender like any other: list its id only if you want it to be able to ask.

What remains. On the `ihc` network it can open a TCP connection to any service: the shared Redis's default user is still open to every container on that network (apps included; a known gap, to be closed), and a vulnerable service there is reachable from it as from any app. Logs can contain whatever an app chose to log. The OpenClaw image downloads channel plugins at first start, and the LLM and the chat channel are on the internet, so it has egress: asked to, it will `git clone` a public repository into its workspace and read it (it did in the conversation run, [`first-run.md`](first-run.md#operator-conversation-run)). It cannot reach the host or the Docker socket from there, but whoever can talk to it can make it fetch and run code inside its own container.

## Rules

- Never store secrets in app manifests, compose files or `.env.example`.
- Never deploy production on pull request events.
- Never run untrusted pull request code with deploy credentials.
- Apply only commits merged into `main`, one apply per app at a time, and record what a deploy will change before changing it.
- Never delete databases, volumes, repositories, stacks, or proxy routes automatically.
- Never overwrite an existing domain or app without an explicit policy.
- Prefer authentication for internal apps by default.
- Prefer automatic port allocation for new apps.
- Keep local `.env` files out of Git.

## Required Validations

Checked by `ihc-app provision` on every deploy (and by `build` and `apply` where said):

- The repository belongs to the organization (the deploy runner serves nothing else) and its name is the app's slug.
- The slug is not one the platform uses and is not registered to another repository.
- The domain is `<slug>.<BASE_DOMAIN>`, and no other route already owns it.
- App manifest is present and valid; compose file present, with the declared service.
- Healthcheck is declared.
- `deploy.port` is `auto`; host ports are dropped.
- No local Postgres, Redis or S3 server; no host networking, privileged mode or Docker socket.
- The build reads only the repository: no `build.secrets`, `build.ssh`, `build.entitlements` or privileged build, no build network other than the default, no context, Dockerfile or additional context outside the repository (checked by `ihc-app build`).
- The release's commit is the head of `main` of `<org>/<slug>` in Gitea, and the run is for `refs/heads/main` (checked by `ihc-app apply`).
- `mcp`, when present: audience and scopes namespaced by the slug, tool paths that are paths, each scope granted to a group; `mcp.tools` entries with `access` read or write, `groups` a list of groups and `people` a list of emails.

Not checked yet: obvious secret values in tracked files.
